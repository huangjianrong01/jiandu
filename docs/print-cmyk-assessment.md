## 零、一句话结论

**矢量部分的 CMYK 化不难（半天到三天），难的两件事都不是"转换"而是"判断"：**
一是**印厂剖面不在本机**（macOS 只带一个 Generic CMYK，没有 Japan Color / FOGRA），
二是**语义分色不能交给 ICC**（ICC 会把正文黑变成 4 色 295% 总墨量的浓黑，印出来是糊的）。

好消息是：我们这份 PDF **只有 8 个颜色常量、零位图、零透明、字体全嵌入**，
这四点凑齐之后，我们离印厂可用的 PDF 比想象中近得多——**离 PDF/X 只差三件事**。

建议路径：**P0 语义分色（3 人日）→ P1 剖面与四框（4 人日）→ P2 专色（先做"配方+预检"0 代码，真注入留待定制）**。
"能拿去印厂"的里程碑 = **7 人日**，一个人两周内可交付。

## 二、Q1 色彩空间转换：RGB → CMYK 无缝映射，难吗？

**结论：技术上不难（一行系统 API），难在"往哪个剖面转"和"转完要不要手工修"。**

### 2.1 系统 API 够用，不需要引入任何 crate（已核对到函数级）

`CGPDFContext` 画 CMYK **全程无栅格化**，PDF 原生支持 `/DeviceCMYK`，矢量依旧是矢量。
现有 `core-graphics 0.24` 的绑定情况（逐个查过源码 `src/context.rs`、`src/color_space.rs`）：

| 需要的能力 | 现成？ | 说明 |
|---|---|---|
| 取一个 CMYK 色彩空间 | ✅ 已绑定 | `CGColorSpace::create_with_name("kCGColorSpaceGenericCMYK")` |
| 把上下文切到 CMYK 填色/描边空间 | ❌ 需 FFI | `CGContextSetFillColorSpace` / `CGContextSetStrokeColorSpace`（**关键**：不切这一步，CG 会把 CMYK 又转回 DeviceRGB，白忙） |
| 造一枚 CMYK 的 CGColor | ❌ 需 FFI | `CGColorCreateGenericCMYK(c,m,y,k,a)`，一行 |
| 落笔 | ✅ 已绑定 | `ctx.set_fill_color(&CGColor)` 就在 `context.rs:195` |
| 按 ICC 剖面转一枚颜色 | ❌ 需 FFI | `CGColorCreateCopyByMatchingToColorSpace(color, intent, space, opts)` |

即：**新增 3~4 行 `extern`**（项目里 `pdf.rs` 已有 2 处先例），
`Brush::rect / line / poly / ellipse / put` 五个函数把 `set_rgb_fill_color` 换掉即可。
`set_fill_color(&CGColor)` 这条"通用"路径已经把工作做完了一半——**这一层的工程量 ≤ 半天。**

> 注意：`kCGColorSpaceGenericCMYK` 就是本机那个 Generic 剖面，能用但不该用来交货，见 §2.2。

### 2.2 真正的第一个坎：本机没有印厂剖面

`Generic CMYK` 是 Apple 给屏幕预览用的"通用"剖面，不是印刷标准。中国的印厂默认是
**Japan Color 2001 Coated**，欧洲是 **FOGRA39 / ISO Coated v2**，北美是 **GRACoL2013**。
用 Generic 去分色，等于让印厂按一套它没听说过的油墨特性去印——**结果不可预测**。

→ **必须自带 ICC 剖面**（随 App 分发或首次运行下载）。许可需要逐份确认：
- ECI 的 `ISO Coated v2 (ECI)` / `Coated FOGRA39`：ECI 授权允许随软件分发，需署名；
- `Japan Color 2001 Coated`：由日本色彩研究所 / JAGAT 管理，Adobe 系产品随包分发，
  第三方再分发条款**需确认**（这是我们唯一需要法务看一眼的地方）。

### 2.3 真正的第二个坎：ICC 转出来的颜色，纸上是不对的（实测数据）

拿当前代码里的 8 个色值做了真实 ICC 转换（`sips --matchTo "Generic CMYK Profile.icc"`，8bit）：

| 用途 | 原 RGB | 实测 CMYK（Generic） | 总墨量 TAC | 印出来会怎样 |
|---|---|---|---|---|
| 纯黑 | `000000` | **74 / 71 / 64 / 87** | **295.7%** | 四色浓黑。中文小字四色套印必糊、边缘带彩边；TAC 踩线，正规印厂会退稿 |
| 标题墨 | `1A1A1A` | 79 / 73 / 68 / 68 | 287.7% | 同上，篇章大字会"发脏" |
| 正文墨 | `101010` | 76 / 71 / 66 / 79 | 291.0% | 同上，且正文是全书出现最多的对象 |
| 朱砂（主用） | `C3272D` | 4 / 93 / 86 / **9** | 192.1% | 带 9% K，朱色被压暗一档 |
| 朱砂（笺读） | `8C2B22` | 14 / 87 / 89 / **31** | 220.4% | **带了 31% K，这就是"发灰发暗"的来源** |
| 浅墨栏线 | `8A7A5C` | 42 / 44 / 66 / 8 | 159.6% | 一根 0.5pt 的版框线是四色叠，套印偏 0.1mm 就出彩色毛边/断线 |
| 纸色 | `F5EFE2` | 3.5 / 3.5 / 8 / 0 | 15.2% | 满版铺 15% 网点：胶印会花、会鬼影，一色偏了整本书"纸色"忽深忽浅 |

「颜色发灰发暗」不是玄学，就是**那个 K 分量**。ICC 的目标是"看起来一样"，
而印刷需要"印出来一样"——两者不等价：

- ICC 把纯黑变成 4 色黑，因为屏幕上 4 色黑确实更黑；
- 但纸上 4 色黑意味着四块版都要套准，否则小字边缘发彩、字口发虚；
- 正文这种"小、密、多"的对象，**必须 0/0/0/100 单黑**——这是所有排版软件
  "黑字用单黑（Black Overprint / 100K text）"选项存在的唯一原因。

### 2.4 我们的结构性优势：可以做「语义分色」而不是「像素分色」

绝大多数软件的 CMYK 是**像素级**的：不知道这块黑是"正文"还是"照片阴影"，只能一律转。
我们不一样——我们是**生成器**，每一次落笔都知道自己在画什么：

| 语义 | 应该怎么分色 | 值 |
|---|---|---|
| 正文主墨（`draw_cell` 的字） | 单黑，禁四色 | `0 / 0 / 0 / 100`（TAC 100%） |
| 篇题 / 榜眼大字 | 单黑，或极轻微暖黑 | `0 / 0 / 0 / 100`；暖调可用 `20 / 15 / 10 / 100`（TAC 145%） |
| 朱砂（句读 / 印记 / 强调） | **K 归零**，做纯正朱 | `0 / 88 / 85 / 0`（TAC 173%）或 +5K 沉稳版 `0 / 90 / 85 / 5` |
| 版框 / 栏线 | **单色**，靠线宽而不靠浅色"淡" | `0 / 0 / 0 / 100`；确实要浅则 `0 / 0 / 0 / 55`（单色 55% 网点） |
| 纸色 | **不印**。选米色 / 仿古纸 | — |

**「纸色不印」是这份评估里最省钱的一条建议。**
- 满版 15% 四色底：要四块版全幅均匀，胶印上是最难做匀的东西；300 页会看到色差；
- 而且它逼着你做"底色出血"（满版铺到裁切线外），成本和废品率都上一个台阶；
- 换成**本色纸**（米黄轻型纸 / 仿古胶版纸 / 宣纸质感特种纸），整本书只印两色（墨 + 朱），
  既复古又是古籍印刷的通行做法，成本还降一半。
- 只有"数码短版 / 单本打样"场景才需要印底色，那时用 `3/3/8/0` 即可。

### 2.5 建议的实现形态：**离线分色表（Runtime 零依赖）**

因为只有 8 个颜色，不需要在导出的每一页跑色彩管理：

```
开发期（一次性）：ICC 剖面 + 语义规则  →  算出目标 CMYK  →  写进常量表
运行期（每页）：  u32 颜色  →  查表  →  (c,m,y,k)  →  set_cmyk_fill_color
```

好处：**零依赖、零浮点、零性能开销、结果 100% 可复现**（同样输入永远同样墨量）。
坏处：用户换主题色（`theme.zhu()` 可换）时表里没有 → 兜底走一次
`CGColorCreateCopyByMatchingToColorSpace` 实时转换（系统 API，不引 crate）。

三个剖面预设装进下拉即可：**JP（Japan Color 2001 Coated）/ EU（ISO Coated v2）/ CN（按印厂给的 ICC 导入）**。
「导入印厂 ICC」这一项很值钱——大印厂都有自己的 ICC，能导入就等于"适配它"。

## 三、Q2 栅格化：PDF 里"大量图片"逐像素转换的开销

**先给结论：今天的成本是 0，因为我们导出的 PDF 里一张图都没有。**

实测确认：`pdf.rs` 与 `share_paint.rs` 的 PDF 路径里没有任何 `CGImage` / `draw_image` 调用；
扫描的原图只在**屏幕侧**渲染（`link_to_paragraph` 的高亮也只是画框），从不进导出文件。
所以"逐像素色彩转换"这个性能问题，**当前不存在**。

它会在什么时候出现：如果做**影印本 / 图文对照**（把扫描原图当底图印出来），
或者"朱批 + 原图"合排。那时才需要算这笔账：

| 场景 | 像素 | RGB 8bit | CMYK 8bit |
|---|---|---|---|
| A4 单页 300dpi | 2481 × 3507 ≈ 8.7 Mpx | 26 MB | **35 MB** |
| A3 对开 300dpi | ≈ 17.4 Mpx | 52 MB | 70 MB |
| 300 页影印本（全入内存） | — | 7.8 GB | **10.4 GB** ❌ |

→ **绝不能整本入内存**。正确做法（三条，按优先级）：

1. **交给 RIP 转，自己不转**。PDF/X-4 允许图片保持 RGB + ICC，由印厂的 RIP 用它自己的
   剖面转（它比我们更清楚油墨）。这是最省、最准的一条——前提是目标印厂接受 X-4。
2. **按条带转换**（strip-wise）：一次只转 256 行，`CGColorConversionInfo` + `vImage` 或
   `CGContext` 搬运，内存恒定在几 MB，与页数无关。估算吞吐：8bit CMYK 是 4 维 CLUT，
   典型 5~15 Mpx/s/核（**估算，需实测**）→ 单页 0.6~1.7 s，300 页单核 3~9 分钟，
   6 核并行约 30~90 秒。这个量级对"一次性导出"完全可接受。
3. **只在导出时降采样**：印刷 300dpi 是硬要求，但如果原图是 600dpi 扫描件，
   先降到 300dpi 再转，像素直接砍 4 倍。

另有两个坑（早知道早省两天）：
- **CMYK JPEG 的 APP14 反转**：Adobe 的 CMYK JPEG 存的是反相值，直接塞进 PDF 会印成负片。
  要么存 TIFF/Flate，要么按 `APP14/Adobe` 标记处理。
- **半调/网点**：不要把"加网"写进 PDF。网线（175lpi / 200lpi）归 RIP 管，写死等于自杀。

**Q2 工作量：当前 0；若做影印本，+5 人日**（含条带转换、降采样、CMYK JPEG 处理、4 页比对）。

## 四、Q3 专色（Spot Color）：能不能单独给朱砂一个墨版？

**结论：值得做，而且理由比"颜色更准"重要得多——但 CoreGraphics 做不到，得绕。**

### 4.1 为什么专色对我们是刚需，而不只是"更专业"

我们的卖点里有一件是**手绘朱砂句读**（7 段贝塞尔墨滴，`SEED_W_OF_H=0.37 / 24`）。
这些墨滴最细处只有一两个像素宽，版框线 `FRAME_INNER_W = 0.5pt`（0.176mm）。

- **四色叠印**：0.5pt 的线由 4 块版拼成，套印误差 ±0.1mm → 线会"胖瘦不均 + 两缘带彩"，
  朱砂墨滴的细尾直接消失。**这是把我们的核心卖点印没了。**
- **单色专色**：一块版、一种墨，边缘锐利，细尾完整，套印只有"与墨版对位"一个变量。

所以专色在这个产品里不是"进阶选项"，是**保住卖点的技术前提**。

### 4.2 CoreGraphics 的硬限制

PDF 支持 `/Separation` 与 `/DeviceN` 色彩空间（一个色版 = 一个墨），
但 **CoreGraphics 不提供任何 API 来创建 Separation 色彩空间**——`CGColorSpaceCreateWithName`
的名字表里没有专色，`CGPDFContext` 也就写不出 `/Separation`。
这不是版本问题，是 API 面积问题，等不到。

### 4.3 四条路，成本差一个数量级

| 路径 | 做法 | 工程量 | 风险 | 评价 |
|---|---|---|---|---|
| **A. 印厂代换** | 我们输出 4 色 CMYK，朱砂固定为 `0/88/85/0`；在交付说明里写明"此值请替换为 Pantone 1795C（或贵厂朱红专色）" | **0 人日** | 依赖印厂愿意做一次全局替换 | ✅ **MVP 首选**。行业常规动作，印厂天天干 |
| **B. 后处理注入** | `lopdf` 读入 → 解压 content stream → 把朱砂的精确算子串换成 `/CS0 cs 1 scn` → 每页 Resources 加 `/Separation` 定义 → 写回 | 3~5 人日 | **高**：CG 输出的浮点精度、算子混用（`rg`/`k`/`sc`）、压缩流、资源字典每页不同；漏改一处 = 那页朱砂变黑 | 能做，但要配一整套字节级回归，否则是定时炸弹 |
| **C. 自建 PDF 书写器** | 不经 CG，自己写 content stream（`re f` / `m l S` / `c` / `BT Tf Tj ET`），字体子集仍借 CG 或 `ttf-parser` | 15~20 人日 | 中（可控但要重写落笔层） | 长期正解。绘制原语只有 5 个，规模意外地小；但这不是"印刷模块"，是"换渲染后端" |
| **D. 双色机直接出两版** | 只印墨 + 专色朱，整份 PDF 两个 Separation，连 CMYK 都不做 | 同 C | 同 C | 古籍印刷的真实主流（双色胶印机便宜一半）。属于 C 的副产品 |

**建议：MVP 走 A，把 C/D 作为"有印厂客户明确要求专色"时的独立立项。**
B 我明确不建议——它的收益（省掉印厂一步手工）远小于它的风险（静默改错颜色）。

### 4.4 专色版本真正需要的是"文档"，不是"代码"

A 路径要交付的东西其实是一张**印刷交付单**（随 PDF 一起给印厂）：

```
墨版 1  正文/版框   100K 单黑
墨版 2  朱砂        CMYK 0/88/85/0  → 建议专色 Pantone 1795C 或贵厂朱红
纸张     不印底色，建议 米黄胶版 80~100g 或仿古轻型纸
版框     0.5pt 单黑（若做浅灰，请用 55% 网点单色，勿四色叠）
注音     印刷时建议下限 ≥4.5pt（见 §7 风险）
出血     3mm（见 TODO_V3 第四节）
```

## 五、我们离 PDF/X 有多远？只差三件事

实测我们的 PDF：**纯矢量、零透明、零图层、字体全嵌入子集、无 RGB 之外的颜色空间**——
这恰好是 PDF/X-1a 要求的大部分前提。

| PDF/X 要求 | 我们现状 | 差距 |
|---|---|---|
| 颜色只能是 CMYK / 专色 / 灰 | 全 RGB | **P0 改掉** |
| 必须有 OutputIntent + 嵌入 ICC | 无 | 需后处理注入（`lopdf` 或 `pikepdf`，1~2 人日） |
| 必须有 TrimBox（+ MediaBox） | 只有页面尺寸 | 与出血 TODO 同一处，`kCGPDFContextTrimBox/BleedBox` 都在辅助字典里，**顺手一起做** |
| 字体全嵌入 | CG 自动子集嵌入 ✅ | 无 |
| 禁透明度 | 无透明 ✅ | 无 |
| 无外部引用/无 RGB 图 | 无图 ✅ | 无 |

→ **"能过 Acrobat Preflight 的 PDF/X-4" ≈ 再 +2 人日**（OutputIntent 注入 + 四框 + 预检脚本）。

## 七、风险清单（按"会不会让客户退稿"排序）

| # | 风险 | 后果 | 处置 |
|---|---|---|---|
| 1 | 正文用 4 色黑（现在 ICC 会这么给） | 小字糊、边缘发彩、被印厂退稿 | P0 强制单黑，加断言：导出后正文墨 D 值必须 = 100K |
| 2 | **注音字号在纸上不可读** | 注音是卖点，印出来是一团墨 | 正文 12pt × `RUBY_SCALE 0.40` = **4.8pt**；下限 `RUBY_SCALE_MIN 0.22` → **2.64pt**。印刷下限约 4.5pt（中文 5pt 勉强、4pt 以下是糊）。**印刷模式下把注音下限抬到 0.38（4.5pt@12pt），或提供"印刷模式关闭注音"开关** |
| 3 | **夹注里的小句读只有 3.4pt** | 夹注块里的「。」会糊成一个墨点 | 夹注正文 = 正文 × 0.5 = 6pt（已在可读下限附近）；注内点状句读再 × `NOTE_PUNCT_RATIO 0.56` ≈ **3.4pt**。屏幕上"轻点"是雅，报纸上是"脏"。印刷模式建议注内句读下限抬到 0.75（≈4.5pt），或干脆在注内用**手绘小墨滴**（我们本来就会画）替代字符句号 |
| 4 | 版框 0.5pt 用四色叠 | 毛边、断线 | 版框统一单色（K100 或 55% 单色网点） |
| 5 | 纸色满版铺 15% 四色 | 花、鬼影、跨页色差 | 默认不印纸色，选纸；数码短版才铺 `3/3/8/0` |
| 6 | ICC 剖面许可 | 上架/法务风险 | 只用 ECI 明确可再分发的剖面；Japan Color 先问 |
| 7 | 出血与 TrimBox 不一致 | 裁切后露白边 | 与出血 TODO 合并做，一次验完（`MediaBox − TrimBox` 四边 = 17.0pt） |
| 8 | 专色后处理静默改错 | 某几页朱砂变黑，且不易发现 | **不做路径 B**，或做则必须"逐页色值断言" |

## 九、需要你拍板的三件事

1. **纸色印不印？** 我建议**默认不印**（选纸），只在"数码短版"开关里保留印底色。
   这条决定 P0 的一大半工作量与整本书的印刷成本。
2. **要不要坚持真专色（路径 C）？** 如果客户是印厂/出版社，值得立项（15~20 人日）；
   如果是"作者自印 / 打样"，A 路径（0 代码）足够。
3. **注音在印刷模式下怎么处理？** 抬下限到 4.5pt（会挤格子）还是给"印刷模式隐藏注音"开关？
   我倾向后者——**卖点可以在屏幕上充分展示，纸上不硬来**。
